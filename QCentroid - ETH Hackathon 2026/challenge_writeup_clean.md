# Quantum-Inspired Classical ML for DDoS Detection

## 1. Problem framing

The challenge is to determine, for each 15-minute network-traffic window, whether DDoS activity is present and, if so, which `src_ip` addresses are responsible. Each dataset contains 100,000 flow rows, while the injected attack traffic is only around 1.5% to 2.5% of total rows, so the main difficulty is detecting a sparse attack signal inside mostly benign traffic.

Although the challenge invites quantum-inspired machine learning, this submission uses a fully classical implementation designed around the same intuition: map structured traffic features into a richer nonlinear feature space and then apply a simple linear classifier.

## 2. Core idea

Instead of classifying individual flows directly, the solution aggregates flows by `src_ip` inside each dataset. This is motivated by the DDoS behavior described in the prompt:

- many suspicious flows come from the same attacking source;
- those flows often concentrate on a narrow set of destinations;
- they show abnormal packet-rate, byte-rate, and traffic-balance behavior.

The system therefore models the problem at the source-IP level and then derives the dataset-level DDoS decision from the highest anomaly score within the dataset.

## 3. Feature engineering

For every `src_ip` inside one dataset window, the notebook computes aggregated features including:

- number of flows generated by the source;
- number of unique destination IPs, ports, and protocols;
- mean and max packet rate (`packets_per_second`);
- mean and max byte rate (`bytes_per_second`);
- mean and max duration;
- total packets and total bytes;
- packet-size statistics;
- average and minimum `outbound_byte_ratio`;
- concentration toward the most common destination IP and destination port;
- protocol shares (`TCP`, `UDP`, `ICMP`);
- share of small-packet flows;
- share of very high packet-rate flows;
- share of low-outbound-ratio flows.

Audit fields such as `scenario`, `split`, `dataset_id`, `burst_id`, and `is_seeded_ddos` are never used as model inputs.

## 4. Quantum-inspired component

The nonlinear embedding stage is implemented with `RBFSampler`, which produces Random Fourier Features. This approximates an RBF kernel feature map and acts as a classical analog of a richer Hilbert-space embedding:

- original source-level features are standardized;
- they are projected into a higher-dimensional randomized nonlinear space;
- a logistic regression classifier is trained on the transformed representation.

This keeps the model fast, interpretable, and easy to justify while still fitting the "quantum-inspired" requirement through feature-space lifting rather than brute-force deep learning.

## 5. Model design

A separate model is trained for each dataset family:

- `family_a`: attack traffic derived from NF-UNSW DoS rows relabeled as DDoS-like;
- `family_b`: benign NF-UNSW traffic with native DDoS attack rows from NF-CSE-CIC-IDS2018.

Training separate models is important because the attack-generation process differs between families, so forcing a single model to absorb both distributions would be less robust.

The final pipeline is:

1. load one dataset;
2. aggregate all flows by `src_ip`;
3. compute source-level engineered features;
4. transform features with `StandardScaler + RBFSampler`;
5. score each source with `LogisticRegression`;
6. classify a dataset as attack if the highest source score exceeds the fixed threshold of `0.5`;
7. output all predicted malicious source IPs as the shortlist.

## 6. Why this works well for DDoS

This formulation matches the structure of the challenge well:

- attacks are sparse at row level but strong at source level;
- attackers concentrate traffic toward a small number of targets;
- high-rate and low-outbound patterns become much easier to separate after aggregation;
- source-level scoring naturally supports both required outputs: dataset flag and source-IP attribution.

It also scales well, because the model processes a few dozen source aggregates per dataset rather than 100,000 rows directly during inference.

## 7. Results

On the provided reduced-schema datasets, the notebook achieved perfect separation on the available validation and test partitions used for offline checking:

- dataset-level detection: F1 = 1.00, AUC = 1.00 for both families;
- source-IP identification: F1 = 1.00 on validation and test for both families.

These results should be interpreted with care because the synthetic benchmark is structured and relatively clean, but they show that the chosen representation captures the dominant DDoS signal very effectively.

## 8. Strengths and limitations

Strengths:

- simple and fast pipeline;
- clear mapping from network-security intuition to model design;
- directly produces the required source-IP shortlist;
- quantum-inspired nonlinear embedding without requiring a quantum backend.

Limitations:

- performance may drop if future attack traffic becomes more stealthy or less concentrated by source;
- the approach assumes source-level aggregation remains informative;
- thresholds and feature definitions may need recalibration on a different network environment.

## 9. Conclusion

This submission shows that a carefully designed classical pipeline can solve the challenge strongly while still using a quantum-inspired modeling idea. The key is not model complexity but choosing the right granularity of representation. By moving from raw flows to source-level behavioral signatures and applying a nonlinear feature map, the system obtains accurate DDoS detection and precise attacker attribution with a lightweight and explainable architecture.
